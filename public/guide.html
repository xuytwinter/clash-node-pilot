Clash Node Pilot

Guide

Run local measurements, preserve manual choices, and switch Mihomo selector nodes only after the policy has enough evidence.

01

First Run

Keep your Clash/Mihomo client and core running, then start Node Pilot from the portable folder:

start-clash-node-pilot.cmd

For source development, use Node.js 22.x and npm start. Open http://127.0.0.1:3210, or the port set with PORT. When the header shows Mihomo connected, the local controller has been read successfully.

02

Manual Test

  1. Select an online proxy client.
  2. Select the writable selector group.
  3. Select the target region.
  4. Leave Switch after test enabled if you want Node Pilot to apply the best result.
  5. Click Test and Select.

Manual results are sorted by one-time latency measurements; automatic optimization uses historical health scoring. Selector writes are reported as switched only after controller readback confirms the new active node.

03

Automation

Automatic optimization periodically tests the current region and applies the same score policy used by the dashboard decision panel.

measure current region→score candidates→apply threshold and cooldown

When the default probe fails for the current region, Node Pilot rechecks the same region with the alternate trusted probe before considering other regions. This reduces unnecessary cross-region changes when a probe target is unavailable. The Node service owns scheduling; Windows watchdog scripts only check local application health, do not terminate Clash, and do not run a second optimization loop.

Manual protection

If an external selector change is detected, automation pauses writes for the configured manual protection window. Monitor-only mode records decisions without changing selectors.

06

Demo and Benchmarks

Use demo mode when reviewing the dashboard without touching real Clash or Mihomo configuration:

npm run demo
npm run demo -- --scenario target-outage

Use the deterministic benchmark harness for policy regression checks:

npm run benchmark
npm run benchmark -- --json

The benchmark starts an isolated fake controller and drives the authenticated local HTTP API. It reports recovery steps, unavailable steps, switches, probe counts, harmful switches and decision codes. Policies use unequal probe budgets; results are simulated rather than measured internet recovery times. See benchmark methodology and tradeoffs. Changing a demo scenario clears runtime history, health, results, manual locks and cooldown. An active job returns HTTP 409 instead.

07

Troubleshooting

The dashboard says the controller is offline
Confirm the proxy client and core are running and that the external controller is enabled.
No nodes appear for a region
Node names may not match the built-in region rules. Edit regions.json for local naming conventions.
The fastest measured node was not selected
Automatic optimization also applies failure history, jitter, threshold and cooldown. Manual tests use one-time latency ranking; monitor-only and manual protection can prevent writes.
A write result is unknown
The selector write or readback failed after commit started. Check the proxy client state before assuming either result.
The page seems stale
The dashboard refreshes automatically every 15 seconds. The refresh button forces an immediate status read.
Upgrade or rollback
Back up state and its .bak before upgrading. Use a separate application folder and preserve the configured state path. Unknown newer schemas disable writes; rollback needs the older application with its matching saved state. Isolated tests do not establish a real-machine upgrade. See compatibility.
API authentication and diagnostics
Get a token from GET /api/session and send x-pilot-session on other API requests except /api/health. This does not block malicious same-user local processes. Diagnostic reports omit names, paths, endpoints and free text, but retain report-local anonymous indices, timestamps and statistics. Review before sharing. See security policy.
